## 提案 1：标签功能优化盘点

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.6.12–17）](../requirements/2026-09-26_tag-enhance/tag-enhance.md)

**现状能力**（基于 `tags.ts` / `TagPickerDialog.vue`）：frontmatter 存储（方案 A）、侧栏标签区（计数角标 / 折叠 / + 新建）、管理弹窗（**搜索过滤**、重命名、删除、改色）、按标签筛选网格、笔记打标签入口（侧栏树 + 网格卡片）。标签 API：list / create(name, color) / rename / delete / setColor / noteTags / add / remove / notesByTag。

**优化点提案**：

| 优化点 | 说明 | 难度 |
| --- | --- | --- |
| 打标签时内联新建 | 见提案 2 | ★ |
| 多标签组合筛选 | 网格筛选目前单标签；支持 AND / OR（侧栏多选 + 「满足全部 / 任一」切换） | ★★ |
| 标签合并 | 把标签 A 的所有笔记并入标签 B（frontmatter 批量改写 + 删除 A），减少标签碎片化 | ★★ |
| 使用频率 / 最近使用排序 | 标签区与打标签弹窗按笔记数或最近使用排序 | ★ |
| 新建标签自动配色 | 新建时从柔和色板自动取色（可后改），省掉选色步骤 | ★ |
| frontmatter 标签可视化编辑 | 所见即所得下 frontmatter 区的 tags 以胶囊展示、可点选增删（装饰 + 与标签系统双向同步） | ★★★ |
| 正文内联 `#标签` 识别 | 正文 `#tag` 语法自动进标签体系——**双源设计决策大**（frontmatter 与正文的写入口、去重、迁移），需单独立项讨论 | ★★★ |

**建议**：打包「内联新建（提案 2）+ 多标签筛选 + 自动配色」做一个小版本；胶囊编辑与内联标签单独立项。

## 提案 2：打标签时内联新建标签

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.6.12）](../requirements/2026-09-26_tag-enhance/tag-enhance.md)

**需求**：给笔记加标签时若无合适标签，直接在弹窗内新建，不用回侧栏点 +。

**方案**：`TagPickerDialog` 的过滤输入无匹配时，列表末尾显示「＋ 新建标签「{关键词}」」行——点击即调 `createTag`（自动从柔和色板取色，可后改）并自动勾选到当前笔记。名称校验复用 `shared/validate`（与侧栏 + 一致）。

**难度 ★，约 0.5 天**（含重名处理与测试）。

## 提案 3：临时笔记（缓冲区）

**需求**：`Ctrl+N` 新建的笔记先写入内存缓冲区（不落盘），专注把想法写下来；`Ctrl+S` 保存时再选择进入的库 / 目录。

**现状**：`Ctrl+N` 直接在「当前位置上下文」的库目录创建文件并打开——想清楚了才建文件，还是想写之前先选位置，打断思路。

**方案设计**：

- editor store 增加**缓冲模式**：`current = { vault: '', path: '', buffer: true }`（无真实路径）；
- 缓冲模式下：**自动保存禁用**（只响应 Ctrl+S）、外部修改 hash 保护跳过、watcher / 双链索引 / 收藏 / 常用 / 标签 / 插件 note:opened 等路径强绑定子系统逐一容错（缓冲笔记对这些不可见）；
- `Ctrl+S` → 弹「保存到…」对话框：复用 `MoveDialog` 的树形目录选择器 + 文件名校验（`shared/validate`）→ `createNote` 建文件 → 写入内容 → 编辑器切换到正式路径，转常规模式；
- 退出保护沿用现有 dirty 机制：有未落盘内容时关闭 / 切换笔记弹「保存 / 放弃」。

**待决问题**：① 单缓冲区（新 Ctrl+N 前提示已有未落盘缓冲）还是多份？建议**单缓冲**；② 心流下 Ctrl+N + 落盘选择器的呈现（浮层样式，与浮层侧栏同思路）。

**难度 ★★★，2~3 天**。轻量替代方案：Ctrl+N 改为「先弹保存位置再创建」（★，零缓冲复杂度，但失去「先写后归类」的核心体验，不推荐）。

## 提案 4：斜杠命令（/ 命令面板）

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.4.22）](../requirements/2026-09-26_slash-commands/slash-commands.md)

**需求**：类似语雀，输入 `/` 触发命令列表，继续输入过滤，选中执行——把编辑动作「命令化」，与手不离键盘的方向一致。

**一致性原则（用户强调）**：斜杠命令 = 既有工具栏 / 快捷键动作的**命令化封装**，行为必须与对应快捷键完全一致（同函数调用）：

| 命令 | 行为（与快捷键一致） |
| --- | --- |
| `/表格` / `/t` | 同 `Ctrl+T`：弹出尺寸提示浮层，输入行列数 |
| `/标题1` … `/标题6`、`/标题0` | 同 `Ctrl+1…6` / `Ctrl+0` |
| `/公式`、`/代码块`、`/引用`、`/任务` | 同工具栏对应按钮 |
| `/分割线`、`/日期` | 插入片段 |

**技术方案**：CM6 补全机制天然适配——新增一个以 `/` 为触发符的 completion source（与 `[[`、锚点补全同源不同触发），选项 `apply` = 执行对应命令或插入片段（completion 机制自带触发文本替换）。命令注册表复用工具栏 / 快捷键的既有函数。

**难点**：① `/` 在正文中是普通字符（URL、日期 `2026/09/26`）——激活策略需明确（建议行首 `/` 或「/ 后接字母」才触发），误触发 `Esc` 关闭即可；② 与 `[[` 补全互斥（CM 自动管理，同时只开一个）；③ IME 组词期的既有经验（冻结机制）复用。

**适用范围**：源码 + 所见即所得均可用（CM 层统一），心流模式自然可用。

**难度 ★★，1~2 天**。

## 提案 5：Vim 模式

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.4.23）](../requirements/2026-09-26_vim-mode/vim-mode.md)

**需求**：vim 键位支持。关注：按键 / 快捷键冲突、系统局限、实现方式（内置 vs 插件）、适用范围。

**关键结论：插件方案在当前架构下不可行**——插件运行在独立进程，插件 API（命令 / 状态区 / 工具栏声明）**没有「编辑器扩展」注入能力**；引入该能力需要跨进程传 CM extension，破坏进程隔离设计且工程远大于收益。→ **内置实现**，且基于官方 `@codemirror/vim` 包（成熟的 normal / visual / insert / replace 完整实现），集成而非自研。

**技术难点与难度评级**：

| 难点 | 说明 | 难度 |
| --- | --- | --- |
| 基础集成 | 设置开关（默认关）+ Compartment 挂 `vim()` 扩展（既有 Compartment 模式照搬） | ★★（0.5~1 天） |
| **快捷键冲突矩阵**（最大工作量） | ① **Esc**：vim 的「返回 normal」vs 全局 Esc 分级回退（退预览 / 退心流）——vim 开启时编辑器聚焦则 vim 优先，全局分级需让位并文档说明；② **Ctrl 系**：vim 的 Ctrl+F（翻页）vs 全局搜索、Ctrl+S 保存（vim 无此键，可共存）、Ctrl+N 新建、Ctrl+R redo——需逐一决策（建议 vim 优先 + `unmap` 个别键）；③ **Alt 系**（Alt+W/T/F…）：vim 一般不吞带修饰键的组合，实测确认即可 | ★★★★（1~2 天，含决策与真机验证） |
| **IME 组词** | normal 模式下 IME 应禁用（vim 惯例，`@codemirror/vim` 有处理）；中文输入 + vim 的组合需真机验证 | 真机，不可预估 |
| 补全交互 | insert 模式补全正常；normal 模式补全应关闭（vim 包已有行为） | ★ |
| 设置与文档 | 设置 → 编辑器新增「Vim 编辑模式」开关 + 冲突速查说明 | ★ |

**适用范围**：源码与所见即所得均可用（都在 CM 层）；**心流 + vim 是自然组合**——vim 用户正是「手不离键盘」的极致，但需接受「Esc 优先级让渡给 vim」的约定（这正是难点①的产品决策）。专注模式同理。

**总体 ★★★☆，2~4 天**。建议先做「最小可用」：开关默认关 + 编辑器内 vim 优先策略 + 冲突速查文档，后续按反馈调。

## 提案 6：分享功能（生成链接）

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.3.10）](../requirements/2026-09-26_share-gist/share-gist.md)

**需求**：把笔记生成链接分享给他人。**核心局限（用户指出）**：笔记库可能是 GitHub **private** 仓库——raw 链接带 token 有泄露风险、无权限者 404，不可长期分享。因此分享的本质是**把内容复制到某个公开 / 半公开的载体**，而非「给私有内容一个链接」。

**方案空间**：

| 方案 | 机制 | 优劣 | 难度 |
| --- | --- | --- | --- |
| **一期：Gist 分享**（推荐） | 用已存 PAT 调 GitHub Gist API，把笔记 Markdown 发布为 **secret gist**（有链接即可见、可随时删除 / 更新），返回链接复制 | 无需服务端、贴合本地优先；**局限**：图片附件不随行（可选 base64 内联，注意大小）；**前置**：现有 PAT 引导只勾了 repo scope，需提示用户补 **gist scope**（token 管理页操作一次） | ★★（1 天：gist API 封装 + 分享对话框 + 更新 / 删除管理） |
| 二期：发布到公开展示仓库 | 把选中笔记渲染成 HTML（复用导出 HTML 管线）+ 图片一并推到用户指定的 **public** 展示仓库（如 `<user>/trace-pages`）的 gh-pages 分支，得到正式发布页 URL | 适合「正式发布的笔记页」、图片可随行；需用户建 public 仓库 + PAT 有该仓库权限；更新 = 再推 | ★★★（1~2 天） |
| 第三方 pastebin / 短链服务 | 调外部 API | 隐私 + 依赖第三方，**不建议** | — |
| 自建分享服务 | 需要服务端 | 违背本地优先理念，**不建议** | — |

**建议**：先做一期 Gist（secret 链接即「生成链接」的最安全实现），二期按需。

## 提案 7：快速引入图片（系统文件选择器）

> **状态（2026-09-26）**：✅ 已立项 → [正式需求（FR-2.5.4）](../requirements/2026-09-26_image-picker/image-picker.md)

**需求**：快捷键 / 功能按钮打开系统资源管理器选择图片文件，复制到笔记库附件目录并生成引用。

**现状**：粘贴 / 拖入图片已自动存附件目录（`attachmentsDir` 可配置）并生成相对引用（FR-2.5，管线为 base64 → `saveImage`）。缺的是「从本地文件选择」的入口。

**方案**：新增一个 IPC（主进程完成全部动作，渲染端一次调用）：

1. `dialog.showOpenDialog`：系统原生多选文件选择器，filter 常见格式（png / jpg / jpeg / gif / webp / svg / bmp）；
2. 选中文件按**既有附件命名规则**复制进附件目录（复用粘贴管线的命名 / 重名处理逻辑，抽成公共函数两处共用）；
3. 返回生成的引用名列表 → 编辑器光标处批量生成 `![](attachments/…)` 引用。

**入口**：工具栏「图片」按钮改为打开选择器 + 新快捷键 `Ctrl+Shift+I`（当前无占用；生产模式无 DevTools 冲突）。

**操作系统差异（用户强调）**：文件选择器是系统原生对话框（Windows / Linux 的差异由 Electron 屏蔽）；路径处理走 `path` API 无感；Linux 的对话框走 GTK portal（Electron 自带，正常）；图片**不做格式转换**（与现有粘贴管线一致，HEIC 等冷门格式兼容性由系统决定，filter 引导常见格式即可）；Electron 非沙盒，选中路径可直接读文件。

**难度 ★~★★，0.5~1 天**。
